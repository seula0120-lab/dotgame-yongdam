# R1 계획 (개정) — 달팽이 우체부: 캐릭터가 맵 위를 한 칸씩 움직인다

근거 문서: GAME_DESIGN.md (v0), AGENTS.md, deep-interview-snail-postman-r0.md, stage-02-intent.md. 이 계획은 코드를 건드리지 않는다. 기획서에 없는 항목은 "결정 필요"로만 적고, 사람이 확정하기 전에는 계획의 사실로 쓰지 않는다.

## 0. 개정 내역
사람이 옵션 B를 확정했다: R1의 4장 = 달팽이 + 이동 가능/불가 타일만. 편지와 우편함은 R2로 미룬다. D1, D10은 확정으로 바뀌었다.

## 1. 목표 (단 하나)

**G1: 달팽이가 16x12칸 맵 위에서 방향 입력 한 번에 정확히 한 칸, 0.60초 동안 움직인다.**

기획서 근거: 2.1 이동 규칙 (한 칸 이동 시간 0.60초, 타일 16x16, 맵 16x12, 논리 256x192, 표시 768x576). R1에 배정된 4장·5장(레벨 1)·6장(팔레트)은 이 목표를 그리기 위한 최소한만 채운다.

## 2. RALPLAN-DR 요약

### 원칙 (5)
1. 기획서가 유일한 기준이다. 기획서에 없으면 만들지 않는다 (AGENTS.md).
2. 애매하면 기획서를 먼저 고치고 사람에게 보인 뒤 코드를 쓴다.
3. 목표 하나, 커밋 하나 (`goal-1:`). 다른 라운드의 일은 하지 않는다.
4. 테스트 기대값은 기획서 숫자에서 가져온다 (0.60, 16, 12, 256x192, 768x576). 코드 동작을 베낀 테스트는 쓰지 않는다.
5. 완료는 테스트 통과가 아니라 사람이 브라우저에서 수용 기준을 확인하는 것이다.

### 결정 요인 Top 3
1. **기획서 빈칸**: 4·5·6장이 비어 있고, 입력 키·이동 중 동작이 문서에 없다. 코드보다 문서 확정이 선행되어야 한다.
2. **수용 기준 부재**: 9장이 R2 담당이라 R1 완료를 판정할 문서 항목이 없다 (결정 D8).
3. **범위 오염 위험**: 이동만 만들 때 편지·타이머·승패 등으로 번지기 쉽다. 10장과 "기획서에 없는 기능 금지"로 차단한다.

### 옵션
**옵션 B (확정 선택): 문서를 최소로 채움 — 4장은 달팽이 + 이동 가능/불가 타일만, 편지·우편함은 R2로 미룬다.** 6장 8색은 R1에 확정한다.
- 장점: 목표 하나에 가장 충실. 범위 오염 최소. 코드 시작이 빠르다.
- 단점: 4장이 "R1에 채운다"로 배정된 것을 일부만 채우므로 문서에 R2 이월 사실을 명시해야 한다. 5장 격자에 편지·우편함 문자가 없어 R2에서 격자를 확장해야 한다.

**옵션 A (기각): 4장 전체(편지·우편함 포함)를 R1에 채움.** 장점: 배정과 일치. 단점: 편지 밀기 동작이 R1 목표로 들어와 한 목표 원칙 위반. 사람이 기각했다.

**옵션 C (기각): 코드를 먼저 만들고 문서에 사후 반영.** AGENTS.md "애매하면 기획서를 먼저 고친다" 위반.

## 3. 순서

### 단계 I. 문서 변경 — 사람 서명 필요 (코드 금지)
I-1. 아래 "사람 결정 항목" 중 미확정 항목(D2~D9, D11, D12)을 사람에게 보여 확정받는다.
I-2. 확정된 값으로 GAME_DESIGN.md를 고친다: 4장(달팽이, 이동 가능/불가 타일만, 편지·우편함은 R2로 미룬다고 한 줄 명시), 5장(레벨 1 격자), 6장(8색 hex), 그리고 이동 입력·이동 중 동작을 담을 위치(2.1 확장 또는 4장 안).
I-3. R1의 수용 기준 항목을 문서에 적는다 (9장은 R2 담당이므로 위치는 D8).
I-4. 상태 줄을 v1로 갱신. 커밋 `design-v1:`. 사람이 문서를 보고 서명.

### 단계 II. 코드 — 서명 후에만
II-1. `test/logic.test.js`: 문서 숫자 기대값 테스트 먼저 작성 (7장).
II-2. `src/logic.js`: canvas를 모르는 순수 함수. 상태를 받아 새 상태를 돌려준다. 한 칸 이동, 시간(초) 누적으로 0.60초 진행.
II-3. `src/levels.js`: 5장 레벨 1 문자 격자를 그대로 복사. 좌표 따로 없음.
II-4. `src/sprites.js`: 달팽이와 타일의 팔레트 인덱스 배열. 색은 6장 8색 hex만.
II-5. `src/strings.js`: UI 문구 한 곳. R1에 확정된 문구가 없으면(D9) 만들지 않거나 비워 둔다.
II-6. `index.html`: 논리 256x192 캔버스, 표시 768x576, 입력 연결, 렌더. 외부 의존 0.
II-7. `node --test test/` 통과 후 사람에게 열어서 볼 것을 알린다. 커밋 `goal-1:`.

## 7. 검증

### node --test (기대값은 모두 기획서 숫자)
- 한 칸 이동 시간 상수 = 0.60초. 0.60초 경과 시 정확히 한 칸 이동 완료, 그 전에는 완료 아님.
- 방향 입력 1회 → 목표 칸이 입력 방향으로 정확히 1칸 (타일 좌표 기준).
- 타일 크기 16, 맵 16x12칸. 논리 해상도 256x192 = 16*16 x 12*16. 표시 768x576 = 논리 x 3.
- 레벨 1 격자가 16열 x 12행.
- D5 확정대로: 맵 가장자리·벽·울타리 방향 입력은 위치가 바뀌지 않음.
- D3·D4 확정대로의 입력 처리.
- 금지: 코드 동작을 그대로 옮긴 테스트, 기본값 테스트.

### 사람이 확인 (브라우저, index.html 열기)
- 캔버스가 768x576으로 보인다.
- 방향키를 한 번 누르면 달팽이가 한 칸, 약 0.60초에 걸쳐 움직인다.
- 벽·울타리·가장자리 쪽 입력에서 움직이지 않는다 (D5 확정 시).
- 색이 6장에 확정된 8색뿐이다.
- 수용 기준 번호는 D8 확정 후 문서의 번호로 보고한다. 9장이 비어 있는 지금은 번호가 없으므로 "완료"라고 말할 수 없다.
