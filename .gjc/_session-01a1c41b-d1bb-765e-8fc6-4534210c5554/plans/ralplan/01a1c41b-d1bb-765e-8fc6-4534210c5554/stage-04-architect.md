## Analysis
### 1. logic/render/input 분할 (시간 기반 0.60초)
- 타당한 분할: logic.js = 순수 `step(state, heldDirection, dt)`; 렌더 = 상태에서 from/to/elapsed로 선형 보간(D6); 입력 = held 상태 관리. 그러나 계획 II-6은 입력·루프·렌더를 모두 index.html에 두고 상태 모양(from/to/elapsed)도 정의하지 않는다. 노드에서 테스트 불가한 부분을 최소화하려면 `src/main.js`로 분리하고 logic 상태가 보간 필요 필드를 노출해야 한다.
- 결정론: 부동소수 초 누적은 경계 테스트(0.599 미완/0.600 완료)를 불안정하게 만든다. 정수 ms(600)와 `>=` 완료 규칙, 완료 프레임의 잔여 ms 이월(D4 연속 이동 시 칸당 0.60초 유지), main의 큰 dt 상한이 필요하다. 9장 위험표 대응("초 단위 누적")만으로는 부족.
- 이동 확정 시점: 충돌 판정을 이동 시작 시점에 하고, 위치(타일)가 변하는 시점을 완료로 정의하는지 명시해야 한다(테스트 "그 전에는 완료 아님"의 의미).

### 2. D3/D4 타이밍 긴장
- D3(이동 중 입력 무시)와 D4(누르고 있으면 이어서)가 이동 중 눌러서 계속 누른 키에 대해 모순. 제안 문장: "이동 중 입력은 저장하지 않는다. 이동이 끝나는 순간 눌려 있는 방향이 있으면 이어서 이동한다." 두 키 동시 입력은 "나중에 누른 키" 등 한 규칙으로 문서화.
- D5(벽 방향 입력 시 이동 없음)에서 키를 누른 채 벽 쪽이면 매 스텝 재시도하되 위치 불변이어야 함.

### 3. 범위 누수 / 누락 결정
- 레벨 1의 실제 16x12 배치(벽·울타리 위치, 달팽이 시작칸)는 D 표에 없고 I-2가 암묵적으로 채운다. 설계 내용이므로 사람 결정으로 올려야 한다.
- 달팽이·타일 도트 모양은 6장에 색만 있고 모양 기술이 없다. 문서에 최소 기술을 쓰거나 결정에 올려라(창작 범위 통제).
- `<title>` 문구는 UI 문구: D9에 포함하거나 R1에서 생략.
- 시작칸 문자는 로드 시 바닥으로 취급하고 상태에서 위치를 얻는다 (격자에 좌표 따로 적지 않는다 규칙과 일치).
- 비누수: sprites/팔레트(6장 R1 배정), 8색 확정은 R1 배정 범위. 방향 표현(D7)은 만들지 않음 — 적절.

### 4. 검증 계획
- "시간 상수 = 0.60", "768x576 = 논리 x3"은 상수와 리터럴 동일성 테스트(동어반복 경계). 행동 테스트(경계 0.599/0.600, 가장자리/벽 불변, 격자 16x12)로 대체, 표시 크기는 사람 확인.
- 사람 확인에 file:// ES module 제약 → `python3 -m http.server 8000` 안내 포함 필요.
- 캔버스 확대 시 image-rendering pixelated 필요(렌더 세부, 문서 변경 불필요).
- 수용 기준 번호 미정 상태에서 완료 선언 금지 — 계획이 이미 반영. 좋음.
