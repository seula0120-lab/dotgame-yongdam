# Architect 검토 (R2 계획, pass 1)

## Summary
계획의 큰 구조(순수 logic.js 확장, 기획서 우선, goal-2/3 분리, R3 범위 제외)는 타당하고 기획서 10장·AGENTS.md와 충돌하지 않는다. 다만 design-v4에 들어가야 할 규칙 의미(배달 확정 시점, 한 프레임 평가 순서, 이동 중 시간 만료, 우편함 의미, 타이머 반올림/시계 모델)가 결정 목록에 빠져 있어 pass 1 기준 HIGH 1건이 막는다. Architectural Status WATCH, Code Review REQUEST CHANGES.

## Claims (검증한 사실)
- logic.js tick: 이동 완료 시 `{pos, move:null}`을 새로 만들어 반환하고 초과 시간을 버린다. 이동 없고 입력 없으면 state를 그대로 반환. 확장 시 필드 유실·타이머 누락 위험.
- isWalkable은 '.'만 true. 'M'을 격자에 남기면 달팽이가 우편함에 못 들어간다. 이는 규칙 결정이다.
- sprites.js는 이미 존재(계획은 '신규'). test/logic.test.js는 `{pos,move}` 리터럴과 `parseLevel(["S#"])`를 직접 쓴다. LEVEL_1은 문자열 배열.
- main.js는 방향만 pressed에 쌓고 e.repeat를 버린다. R/시작 키 경로 없음. index.html은 256x192 캔버스를 768x576로 pixelated 확대.
- GAME_DESIGN.md 2.1: 편지 밀기, 막힘, 배달, 클리어, R=현재 레벨 처음 상태는 이미 확정. 2.2는 제한 시간 고정값/숫자는 격자 옆/시간 다 되면 패배만 확정. 3장·4장 편지·우편함·7장 텍스트·타이머 표시 여부는 비어 있음.

## Analysis
### 1. 순수 logic.js 확장 (구조 OK, 형태 지정 필요)
- 권고 형태: level(불변) = rows + start + letters 초기 위치 + mailbox 위치 + timeSec; state(가변) = pos, move(밀리는 편지 index 포함), letters, delivered, remainingMs, status('playing'|'won'|'lost'). 레벨 파싱 때 L은 '.'로 치환해 letters로 분리(S와 같은 방식), M은 rows에 남기되 편지 도착 판정만 별도 함수.
- 편지 커밋 시점: 이동 완료(600ms). 편지 렌더는 달팽이와 같은 t로 선형 보간(계획 11장 제안 타당). 이동 중 입력 폐기이므로 이동 중 논리 충돌은 없다.
- 밀기 판정 함수: 달팽이 목표칸이 편지 -> 편지 뒤 칸이 (바닥 또는 우편함) 이고 다른 편지 없음이어야 이동 시작. 편지 연쇄 밀기 없음(규칙상 막힘).
### 2. 타이머 결정성과 DT_CAP
- 타이머를 캡된 dt의 합(게임 시간)으로 두면 tick은 순수·결정적이고 이동(2.1.1)과 같은 시계라 일관된다. 대가: 프레임이 느리거나 탭이 숨겨지면 실시간보다 느리게 줄어든다(일시정지 우회). 기획서 2.2에 '게임 시간 기준, 캡 적용'을 한 줄 명시하고 사람이 수용해야 한다. 벽시계 방식은 비결정적이고 이동과 불일치해 비권장.
- 이동 완료 프레임의 초과 시간 폐기는 이동에만 적용. 타이머는 매 프레임 캡된 dt 전부 감산(HIGH 아닌 MEDIUM 함정, finding 참조).
- 평가 순서(제안): 이동 진행/완료 -> 완료 시 배달 반영 -> 전부 배달이면 won(클리어 우선, R2-14) -> 아니면 remainingMs -= dt -> <=0이면 lost(이동 중이면 이동 폐기, 편지 커밋 안 함) -> won/lost 이후 tick은 불변.
- 표시 반올림은 ceil(remainingMs/1000): 0 표시는 remainingMs==0일 때만. 그렇지 않으면 R2-13(시간 남았는데 실패 아님)과 R2-6이 어긋난다.
### 3. 푸시 규칙 vs 0.60초 이동
- 기획서가 '편지를 밀 때도 같음'이므로 이동 시간은 단일 상수 MOVE_MS 하나로 충분. 밀기 가능 여부 판정은 이동 시작 시점에, 위치 커밋은 완료 시점에. 막힌 밀기는 이동 자체가 시작되지 않는다(달팽이도 정지) - R2-3과 일치.
- 결정 필요: 우편함에 달팽이 진입 가능 여부, 우편함 수용량(편지 2개 + 우편함 1개 제안이므로 무한 수용이 아니면 클리어 불가), 배달 후 편지 소멸 vs 우편함 안에 표시(R2-4).
### 4. R키 의미
- R = createState(level) 호출 한 번. 별도 reset 로직 금지. 플레이/이동 중에도 즉시 적용(이동 폐기). 같은 프레임 방향 입력은 폐기. 타이틀 R 무시, 클리어/실패 R은 플레이로(기획서 2.1은 '현재 레벨 재시작'만 확정; 클리어/실패 화면 규칙은 3장에 (에이전트 제안)으로 신설).
- 시작 키(Enter) 프레임의 방향 입력은 폐기. e.repeat는 모든 액션 키에 적용. Ctrl/Meta+R은 무시.
### 5. 화면 상태
- screen을 저장하지 말고 `started`+play.status에서 파생(진실의 원천 1개). main.js 입력 큐에 액션 종류 추가.
### 6. 문서 우선 순서
- AGENTS.md 원칙(기획서 먼저)에 부합. 옵션 C 탈락은 정당. 옵션 B는 goal-2에 종료 표시·R이 없어 검증 데드엔드, D7 로직의 goal-3 교체, 2.2/7장/9장 이중 수정을 만든다 -> '규칙은 design-v4 한 번 서명, 텍스트·폰트만 분리 서명' + 코드 goal 2개 유지를 권고. 7장 UI 텍스트는 T2(기획서에 문구를 적고 strings.js는 복사)가 AGENTS.md '기획서가 유일한 기준'과 맞다. T1은 서명 안 된 문구가 코드에만 존재.
- 클리어 가능성: 되돌리기 없는 푸시 퍼즐. 해법 키열을 기획서에 적고 재생 테스트(기획서 기대값 테스트).
### 7. 범위 이탈 점검
- Space+방향키, 사운드, 점수, 레벨 2·3, 위험물 오브젝트는 계획에서 올바르게 제외. '위협'을 타이머로만 해석한 것은 타당(기획서에 위협 오브젝트 없음). 타이머를 화면에 표시하는 것 자체가 기획서에 없는 결정이므로 D5로 이미 올린 것은 적절. 문제 범위 이탈은 없고 오히려 규칙 의미 누락이 문제.

## Root Cause
계획이 '값'의 결정(D1~D16)은 꼼꼼히 나열했지만 '의미/순서'의 결정(언제 확정, 어떤 순서로 판정, 시계 모델)을 문서 항목으로 올리지 않았다. 이 둘이 R2-14·R2-7·R2-13 같은 수용 기준의 경계 동작을 결정한다.

## Findings
1. HIGH - stage-01-planner.md 4장/8장: 규칙 의미 6건 누락(배달 확정 시점, 프레임 평가 순서, 이동 중 만료, 우편함 진입·수용량, 타이머 반올림, 시계 모델). 수정: D17~D22 추가하고 design-v4 2.2/4장에 명문화.
2. MEDIUM - src/logic.js tick: 완료 분기 조기 return이 타이머 감산 누락·필드 유실 유발. 수정: 스프레드 + 이동/판정/타이머 단계 분리, 불변식 테스트.
3. MEDIUM - test/logic.test.js, levels.js, sprites.js: 상태 리터럴·parseLevel(grid)·LEVEL_1 배열 형태 파급 및 sprites.js 기존재 오기. 수정: LEVEL_1 배열 유지 + 시간은 옆 export, 영향 테스트 정리를 계획에 명시.
4. MEDIUM - 계획 D16: fillText 안티앨리어싱이 8색 규칙(R1-5/R2-8)과 충돌 가능. 수정: 타이머는 비트맵 숫자 글리프, 한글은 도트 웹폰트 정수 좌표+로딩 대기, 8색 확인 방법 지정.
5. MEDIUM - src/main.js·계획 6장: screen/status 이중 상태, 방향 전용 입력 모델. 수정: screen 파생, 액션 입력, 키 우선 규칙.
6. MEDIUM - 계획 7장: 옵션 B의 검증 데드엔드·이중 서명, 해법 재생 테스트 부재. 수정: 규칙 1회 서명, 해법 키열을 기획서에 기록.
